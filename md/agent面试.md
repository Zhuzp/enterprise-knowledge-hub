**1.RRF公式：**
    RRF(d) = Σ  1 / (k + rank_i(d))
    就是挨个遍历每一路的检索结果：1/(k+rank_i(d)),K常用60，rank_i(d)是文档在当前检索的排名，然后求和。

**2.RRF 为什么用排名而不用各路的相似度分数加权?**
    不同检索器的相似度分值不在同一个数值空间，不能直接加权相加；但排名是归一化后的相对顺序，天然可融合。
**2-1.那我把三路分数各自做min-max归一化到[0,1]再加权，不就在一个空间了吗？**
    关键在归一化的 min 和 max 是从当前这批候选里取的，不是固定标尺。由此三个问题：
  - 每路的 top1 永远被拉成 1.0，不管它是不是真的好。某一路这次啥都没召回对，它的第一名照样得满分，和另一路真正命中的文档
    平起平坐——垃圾被抬举了。
  - 分布形状不一样，拉伸会造出假差异。 向量分数通常挤在一起（0.82 / 0.81 / 0.80），BM25 是长尾（31 / 12 / 8）。min-max
    把向量那一簇硬拉满 [0,1]，本来几乎无差别的三条变成 1.0 / 0.5 / 0.0。
  - 召回条数少的时候彻底失效：BM25 只返回 2 条，就是一个 1.0 一个 0.0。
  再加上权重得跟着 query 调。RRF 只用序数位置，绕开了尺度和分布——这才是它简单但好用的原因。

**3.k=60在控制什么？**
    k用来控制：排名靠前的文档，它的排名红利衰减速度
**3-1.把k从60调到1，和调到1000，检索结果各会往哪个方向变化?**
  - k→1：头部陡峭，某一路的第一名能凭一己之力压过另外两路的共识。等于"谁最自信听谁的"，单路出错就直接污染最终结果。
  - k→1000：曲线几乎全平，退化成投票——只看文档在几路里出现过，具体第几名几乎不影响。三路都排 50 名的文档会赢过两路排第 1
    的文档，细粒度顺序丢了。

    原始 RRF 论文做了大量检索评测，**在通用文本检索场景下 k=60 综合效果最优**：
    既不会完全抹掉排名优势，又不会让单一路的 top1 直接垄断结果，完美适配「多异构检索融合」。
**3-2. 三路各取 topK 多少、RRF 融合后送几条进 LLM，这两个数字你怎么定？**
  **我要听的不是"我取 20 融合后取 5"，而是为什么是这两个数——上界受什么约束、调大调小分别在牺牲什么。**
  - 上界的瓶颈是reran，不是检索。检索20条和50条的差别很小，但是cross-encoder rerank是每个候选做一次前向，延迟和候选数近似线性。20-60时成倍的。
  最终条数受两个约束：
    1. token预算
    2. 注意力稀释
    数量级大致是 每路20-50  融合后去前20-30  rerank  最终送3-8条
    上界是从延迟预算倒退出来的
    面试里被问到就这么答，然后补一句"我目前是按经验值 50/20/5起步，还没做延迟和效果的实测"。
  - 调大可能会有一些垃圾文件进池子，占rerank名额。查找时延迟和索引负载上升
  - 调小的牺牲时某路排的靠后但唯一正确的证据进不了池子

**3-3. 给我一个具体查询——纯向量召回不出来、但 BM25 能召回的。**
  - 报销系统里费用类型 6601.08 应该选什么？
  - 市内交通补贴报销请选择费用类型编码 6601.08（市内交通费），勿与 6601.07（出差交通费） 混用。
  - 向量检索是会检索出那条相似度高的，在这里就会出错，检索出6601.07。
    而BM25是经典稀疏关键词检索打分算法，一个词越稀有，IDF值越高（逆文档频率），在BM25打分权重越大。与向量检索天然互补。

**Tool 调用失败怎么处理？**
  

**用户上传一份 PDF 之后，从文档入库到最终能被 AI 问答检索到，中间完整链路是怎么走的？**
用户上传 PDF 后，上传接口先做文件类型、大小、权限等校验。校验通过后，原文件会存入 MinIO，同时在 PostgreSQL 中写入一条文档元数据，状态设为 pending。
为了避免大文件解析阻塞接口，我会把文档 ID 投递到异步任务队列，比如 RabbitMQ 队列。后台 worker 拿到任务后，从 MinIO 下载文件，解析 PDF 文本，做清洗和语义分块。
分块之后，每个 chunk 会写入 PostgreSQL，用于后续引用溯源；同时生成 embedding 写入 pgvector，写入 Elasticsearch 建 BM25 关键词索引，再通过 LLM 抽取实体关系写入 Neo4j。全部处理成功后，文档状态更新为 ready，失败则更新为 failed 并记录错误日志。
用户提问时，先做权限过滤，再并行走向量召回、ES 关键词召回和图谱召回，三路结果通过 RRF 融合，再经过 Rerank 重排，最终把高质量 chunk 和图谱三元组拼成上下文送入 LLM 生成答案，并返回引用来源。

**为什么要做 RRF 融合？**
**如果 ES、向量检索、图谱检索三路结果的分数体系不一样，你怎么把它们合并成一个最终排序？**
因为 ES BM25、向量相似度和图谱召回的分数体系不一致，不能直接加权相加。RRF 用的是排名而不是原始分数。  
具体做法是遍历每一路召回结果，对每个文档按 1 / (k + rank_i(d)) 计算贡献分，k 一般取 60，最后对同一个文档在多路召回中的贡献分求和。这样如果一个 chunk 同时在向量和关键词召回中排名靠前，它的总分会更高。  
RRF 之后我会取 Top N 候选，再交给 Rerank 模型做更精细的相关性排序。

**你说 RRF 后还要 Rerank。那 Rerank 和向量检索有什么区别？**
**为什么不直接用向量检索 TopK 给 LLM？**
向量检索通常是 bi-encoder 模式，query 和 chunk 分别编码成向量，然后通过向量相似度做 ANN 召回，优点是快，适合从大量文档里粗召回。
Rerank 通常是 cross-encoder 或 reranker 模型，会把 query + chunk 放在一起重新计算相关性，能捕捉更细粒度的语义关系，但成本更高，所以一般只对 RRF 后的 TopN 候选做重排。  
不直接把向量 TopK 给 LLM，是因为纯向量检索对专有名词、编号、时间、精确字段、否定条件这些场景容易误召回，而且 TopK 里可能有重复或弱相关内容。Rerank 可以提高最终上下文质量，减少 LLM 幻觉。

**从一段 chunk 到 Neo4j 里的节点和边，中间怎么抽取实体和关系？**
**你怎么控制 LLM 抽取出来的结构稳定，不要乱输出？**
我会先把 chunk 连同抽取规则一起喂给大模型，通过 Prompt 约束它只输出固定 JSON 结构，比如实体列表、关系列表、实体类型、证据片段、来源 chunk_id 等。
为了保证输出稳定，我会配合 JSON Schema / Pydantic / function calling 这类结构化输出约束，降低模型乱格式的概率。
如果输出不合法，就做一次校验和重试；同时把温度调低，并在 Prompt 里给少量示例，让模型尽量按统一格式抽取。
抽取完之后，再做实体归一、别名合并和关系去重，最后落到 Neo4j。
实际上我不会直接把原始 chunk 全量抽给模型，而是先做分段和上下文裁剪，避免超 token，同时只保留对抽取最有用的内容。

**你怎么做 实体对齐 / 去重？**
我会先做规则归一化，比如去空格、大小写统一、符号标准化、别名词典映射，先把明显同义的候选压缩掉。
然后把实体名和上下文一起做向量化，先用相似度召回候选集，再交给 LLM 做最终判定，确认是否同一实体。
合并时不会直接覆盖原始信息，而是保留一个 canonical node，把别名、来源 chunk、抽取置信度都挂在属性里，便于回溯和审计。
如果不同来源给出的属性冲突，我会保留多来源证据，按时间或置信度做优先级。

**图谱建好以后，问答时你怎么把它用起来？**
**比如用户问“某制度对应哪个部门、再关联到哪个流程”，这种多跳问题，你在 Neo4j 里怎么查，怎么把图谱结果和文本检索结果一起送给 LLM？**
我会先做 query understanding，抽取用户意图、实体和约束条件。
然后做 entity linking：先走别名表做精确匹配，匹配不到再用向量召回 entity 候选 Top5，最后交给 LLM 在候选里选最合适的节点。
节点确定后，按照关系白名单做固定 hop 的图谱遍历，返回子图三元组。
最终把图谱证据和文本检索 chunk 一起融合、去重、rerank，再送入 LLM 生成答案。

**如果 LLM 选错了节点，或者候选里都差不多，你怎么兜底？**
我会给 entity linking 设置信心阈值。
如果是高置信度单选，就直接按该节点继续图谱查询；如果是低置信度或者多候选接近，就并行查多个候选子图，最后把结果融合后再排序。
如果实体链接失败，或者图谱里没有足够证据，就自动回退到向量检索 + BM25 检索，保证系统有答案可回。
这样图谱负责精确关系推理，文本检索负责兜底召回。
我不会让图谱查询成为唯一通路，而是把它设计成“增强召回”，这样鲁棒性更好。

**如果让我听你讲，你怎么用 StateGraph 把“意图识别 -> 查询重写 -> 检索 -> 图谱推理 -> 生成 -> 引用溯源”串起来？**
**为什么不用一个普通的顺序链，而要用图状态机？**
我会先做意图识别，把问题分成闲聊、单跳事实、多跳关系、需要图谱推理、需要检索兜底几类。闲聊直接短答；如果是明显不适合图谱的问题，就走向量检索；如果是多跳关系问题，就优先进入图谱链路。
如果实体识别不够明确，或者检索结果太少，我会先做 query rewrite，把原始问题改写成更适合检索和图谱查询的形式。
然后并行做向量、BM25 和图谱召回，召回结果先做 RRF 融合，再经过 rerank 重排。最后把 state 里的原始问题、重写问题、文本片段、图谱推理链路和来源 id 一起交给大模型生成答案，并返回引用来源。
用 StateGraph 的好处是每一步的状态都显式可见，便于分支控制、调试和回溯。比如意图识别后可以条件路由，不同问题走不同链路，不会让所有请求都硬走同一条长链。

**如果一个用户没权限看某些文档，但这些文档恰好在检索结果里，你怎么保证它们不会进入 LLM 上下文？**
**你是检索前过滤，还是检索后过滤？为什么？**
我会在文档入库时，把权限元数据一起写入索引，比如 owner_id、department_id、visibility、allowed_roles。
ES 和向量库里都会带这些 metadata，Neo4j 的节点和边也会保留 allowed_roles 或来源文档权限。
查询时先根据当前用户身份、部门、角色计算可访问范围，然后把权限条件下推到 ES filter、向量库 metadata filter 和 Neo4j Cypher 条件里，保证无权限内容在召回阶段就不会返回。
检索后我还会做一次二次校验，因为融合、重排和图谱扩展过程中可能混入关联数据，最终进入 LLM 上下文前必须再过滤一遍。
检索前过滤负责安全边界，检索后过滤负责兜底防漏。

**用户同时有多个角色，文档也可能是部门可见、公开可见、个人私有。**
**你会怎么设计这个权限过滤条件？**
**比如 ES / 向量库 / Neo4j 分别怎么表达？**
我会把权限拆成几类 metadata：visibility、owner_user_id、dept_ids、allow_role_ids。
visibility = public 表示全员可见；visibility = dept 表示部门可见，需要用户的部门 ID 命中文档的 dept_ids；visibility = private 则要求 owner_user_id = current_user_id；如果配置了角色权限，则要求用户角色和 allow_role_ids 有交集。  
在 ES 里可以用 bool should 表达，只要满足 public、部门命中、本人私有、角色命中任一条件即可。
向量库也尽量用 metadata filter 做前置过滤，如果向量库过滤表达能力有限，就扩大召回 TopN 后做应用层二次校验。
Neo4j 查询时，在节点和关系上保留权限属性，多跳遍历时每一跳都加权限 WHERE，避免扩展出无权限子图。
最后在融合和进入 LLM 前再统一校验一遍，防止图谱扩展或重排阶段混入越权证据。
*ES 大概可以这样描述，不一定要写完整 DSL：*
{
  "bool": {
    "filter": [
      {
        "bool": {
          "should": [
            { "term": { "visibility": "public" } },
            { "terms": { "dept_ids": ["d1", "d2"] } },
            { "term": { "owner_user_id": "u1" } },
            { "terms": { "allow_role_ids": ["admin", "hr"] } }
          ],
          "minimum_should_match": 1
        }
      }
    ]
  }
}

**你项目里用了 Mem0 / 滚动摘要 做会话记忆。**
**那我问一下：RAG 问答里为什么需要记忆？你怎么决定哪些内容写入长期记忆，哪些只保留在当前会话窗口？**
RAG 问答里需要记忆，主要是为了支持多轮追问。比如用户先问“这个制度的审批流程是什么”，后面接着问“那谁负责最终审批”，第二个问题里没有完整实体，需要从会话上下文里补全“这个制度”。  
我会把记忆分成三层：
第一层是当前窗口，保留最近几轮原始消息，用于短期追问。
第二层是滚动摘要，把较早对话压缩成一段 summary，减少 token。
第三层才是长期记忆，比如用户偏好、常问部门、默认数据范围等，这类稳定信息可以交给 Mem0 或单独存储。  
原始会话消息会持久化到 PostgreSQL，方便历史查询和审计；Redis 更适合存短期上下文、session 缓存、摘要缓存。不是所有聊天都写长期记忆，只有稳定、有复用价值、且不涉及敏感内容的用户偏好或业务上下文才会进入长期记忆。

**那你怎么判断一段内容适不适合写入 Mem0 长期记忆？有没有什么过滤规则？**
我不会把每轮对话都写入 Mem0。长期记忆只存稳定、可复用、用户授权或明显表达的信息，比如用户所属部门、常用业务范围、回答偏好、输出格式偏好。  
不会存制度内容、检索结果和 AI 回答，因为这些应该来自知识库本身，否则文档更新后记忆可能变成过期信息；也不会存隐私信息、敏感数据，或者模型推断出来但用户没有明确确认的兴趣。  
实现上可以先用规则过滤，再让 LLM 做一次 memory candidate 判断，输出 should_remember、reason、memory_type、content，只有通过白名单类型和敏感信息检查后才写入 Mem0。当前会话上下文则用最近几轮消息 + 滚动摘要解决。

**你项目里提到 LangSmith / LangFuse 做可观测。**
**那你具体会观测哪些指标？**
**如果线上用户反馈“AI 答非所问”，你怎么通过 Trace 定位是检索问题、Prompt 问题，还是模型生成问题？**
我会先看一次请求的完整 trace，包括 query rewrite、retrieve、graph retrieve、RRF、rerank、generate 这些节点的输入输出、耗时、token 和异常。  
如果用户反馈答非所问，我会先看 retrieve / fuse_rerank 节点的 TopK chunk。
如果 TopK 本身就不相关，说明是召回问题，继续检查分词、query rewrite、embedding、BM25 权重、权限过滤是否过窄。
如果相关 chunk 查到了但没有进入 prompt，说明是融合排序或上下文截断问题，需要看 RRF / rerank 排名、token 裁剪策略。
如果相关 chunk 进了 prompt，但答案仍然错，说明更可能是生成阶段问题，需要加强系统 Prompt、降低温度、换模型，或者加引用一致性校验。  
指标上我会看召回命中率、TopK 相关性、无答案率、引用覆盖率、平均延迟、token 消耗、异常率和用户反馈分数。

**假设用户问：“报销制度里，出差住宿标准和审批人分别是什么？”**
**这个问题需要从两个不同 chunk 甚至两个文档里找信息。**
**你怎么避免 LLM 只回答其中一半？你在检索、上下文组织和生成阶段会怎么处理？**
我会先做 query decomposition，把问题拆成两个子问题：
一个查“出差住宿标准”，另一个查“审批人”。  
然后两个子问题分别走检索链路，各自拿 TopK，最后对 chunk 做去重、融合和 rerank。组织 prompt 时按子问题分组放证据，而不是把所有 chunk 混在一起。  
生成阶段要求模型按子问题逐条回答，并且每一条都必须带引用。如果某个子问题没有检索到证据，就明确回答“根据现有资料未找到”，避免模型补全。

**你用了知识图谱以后，肯定会遇到图谱质量问题。比如 LLM 从文档中抽错关系，或者抽出一些无意义实体。**
**你怎么评估和提升图谱质量？**
图谱质量我会分三层评估。
第一层是抽取质量：抽样检查实体类型、关系类型、证据片段是否正确，比如实体准确率、关系准确率、重复节点比例。
第二层是图结构质量：看孤立节点比例、重复实体比例、关系密度、热门实体的邻居是否合理。
第三层是问答效果：对一组多跳问题做评测，看引入图谱前后答案准确率、引用覆盖率和无答案率有没有改善。  
提升方面，首先会限制实体类型和关系类型，只允许抽取白名单内的结构，比如“部门、制度、流程、角色、系统”；其次要求每条关系必须带 source_chunk_id 和 evidence，不能溯源的关系不入库。  
入库前做格式校验、重复合并和置信度过滤；入库后定期跑质量检查，比如孤立节点清理、别名合并、低置信关系复审。线上如果用户反馈某条答案错误，会回溯到对应的三元组和来源 chunk，再修正抽取 Prompt 或实体对齐规则。

**你项目里用了 arq / Redis 做异步任务。**
**为什么文档解析和建索引不直接在上传接口里同步做？**
**异步任务失败了怎么办？怎么保证文档状态一致？**
文档解析、Embedding、ES 索引和图谱抽取都可能是耗时任务，尤其是大 PDF 或 Office 文档。如果放在上传接口里同步执行，接口容易超时，也会占用 Web worker，影响其他请求。所以上传接口只负责校验、上传原文件、写元数据，然后把文档 ID 投递到 arq / Redis 队列，后台 worker 异步处理。  
状态一致性上，我会给文档设计状态流转：pending -> processing -> ready / failed。上传成功后是 pending，worker 开始处理时改成 processing，所有索引写入成功后改成 ready。如果中间失败，就记录错误原因并改成 failed。  
失败处理有几层：第一是任务队列配置重试次数和退避策略；第二是处理逻辑尽量幂等，比如重试前先清理旧 chunk、ES 索引、图谱关系，避免重复写入；第三是提供手动重新解析 / 重新索引接口。  
如果 MinIO 上传成功但数据库写入失败，就删除 MinIO 文件做补偿；如果数据库写入成功但后续索引失败，文档保持 failed，原文件保留，方便重新处理。

**如果一个文档已经 ready，用户重新上传了新版本，你怎么做增量更新？**
**是全量删除重建，还是只更新变更的 chunk？怎么设计更合理？**
我项目当前会优先采用全量重建。因为文档版本更新后，chunk 边界、实体关系、向量索引和图谱关系都可能变化，如果做增量 diff，复杂度会比较高，也容易出现旧索引残留。  
所以我会先把旧版本的 chunks、向量索引、ES 索引和 Neo4j 中由该文档产生的实体关系清理掉，再按新文件重新解析、分块、抽取和建索引。这样实现简单，状态一致性更容易保证。  
如果后续文档规模变大，可以再优化成基于 chunk hash 的增量更新：对每个 chunk 计算 hash，只重建新增或变更的 chunk，未变化的 chunk 复用原索引；图谱关系也通过 source_chunk_id 定位，只删除变更 chunk 产生的关系。

**你项目里用 pgvector + HNSW。那你讲一下 HNSW 是什么？为什么向量检索里常用它？它有哪些参数会影响召回和性能？**
HNSW 是一种近似最近邻搜索算法，全称是 Hierarchical Navigable Small World。可以把它理解成一个多层图索引。  
它会把向量组织成一个分层图结构，搜索时先从高层快速定位大概区域，再到底层做更精细的邻居搜索。相比暴力计算所有向量距离，HNSW 查询速度快很多，所以常用于向量数据库和 pgvector 的 ANN 检索。  
常见参数有两个：m 和 ef_search。
m 控制每个节点连接多少邻居，越大召回越好，但索引更大、构建更慢。
ef_search 控制查询时搜索候选数量，越大召回越高，但查询越慢。
还有 ef_construction，影响索引构建质量，越大索引质量更好，但构建更慢。
*面试一句话*
HNSW 是一种基于分层小世界图的近似最近邻索引。查询时从上层图快速导航到底层邻近区域，避免全量扫描。它的优势是查询快、召回效果好，适合大规模向量检索。关键参数是 m、ef_search、ef_construction，分别影响图连接度、查询召回和索引构建质量。

**你说 ES 做 BM25 检索。BM25 和向量检索各自适合什么场景？为什么企业知识库里要两个都用？**
向量检索更擅长语义相近、表达不同的问题，比如用户问法和文档说法不完全一致。BM25 更擅长精确词、专有名词、编号、制度条款、产品型号、人名、部门名这些关键词匹配。  
企业知识库里经常有流程编号、制度名称、工单号、系统名，如果只用向量检索，可能语义相似但关键实体不对；只用 BM25，又无法处理同义改写。所以两者结合能提高召回稳定性。

**项目中用了什么大模型，向量的模型用的哪个，rerank用的哪个**
开发阶段我主要用 qwen-plus，因为中文效果稳定、成本适中，也方便在国内环境调试。生产环境我不会固定单一模型，而是做模型路由：普通知识问答走 qwen-plus 或 deepseek-v4-flash，复杂推理、多文档归纳、关系分析类问题再走 deepseek-v4-pro。这样能在效果、延迟和成本之间做平衡。
Embedding 我会和生成模型分开选，优先用 text-embedding-v4，召回后再用 qwen3-rerank / bge-reranker 做重排。RAG 的效果不是只靠生成模型，Embedding、分块、混合检索和 rerank 影响更大。
*如果是面向国外客户*
如果项目面向海外用户，我会优先选 OpenAI 或 Anthropic 这类全球通用模型。生成侧默认用 GPT-5.6 Terra，复杂推理再升级到 GPT-5.6 Sol 或 Claude Sonnet 5；Embedding 用 text-embedding-3-large，因为它对英文和非英文任务都比较强。系统层我会保留模型路由，按成本、延迟和任务复杂度切换。

用langgraph的流程


1. 设计并实现文档接入与异步处理链路，文件上传后先存入 MinIO 和 PostgreSQL，再通过 RabbitMQ 投递解析任务；审核通过后通过 fanout 消息同时触发向量索引和知识图谱构建，实现上传、解析、审核、索引解耦。
2. 实现统一文档解析管线，将 PDF、DOCX、Markdown、TXT 等文件统一解析为 Markdown，并支持提取文档内图片上传 MinIO、通过 OCR 补充图片文本内容，为后续分块、向量化和检索提供标准化输入。
3. 扩展多模态知识接入能力，建设图片 OCR、音频 ASR、视频分片、关键帧抽取和视频画面理解链路，将图文、音频、视频等非结构化资料转换为可索引的 Markdown 知识内容，提升企业知识库的数据覆盖范围。
4. 实现文本分块与索引构建能力，采用带 overlap 的字符分块策略，并优先在段落、换行和句子边界切分；对分块内容批量生成 embedding，写入 PostgreSQL pgvector，同时同步写入 Elasticsearch 作为关键词检索索引。
5. 构建混合检索链路，融合 Elasticsearch BM25 关键词召回、pgvector 语义向量召回和 Neo4j 图谱召回，通过 RRF 进行多路结果融合，并接入 Qwen3-Rerank 对候选 chunk 精排，提升复杂问题下的召回质量。
6. 基于 LLM 抽取文档 chunk 中的实体和关系，写入 Neo4j 构建知识图谱；问答时支持根据问题实体进行 1 到 2 跳关系扩展和关联 chunk 召回，增强跨实体、跨文档问题的推理能力。
基于 LangGraph 实现 Agentic RAG 问答流程，设计 analyze -> rewrite -> hybrid -> graph -> generate 的状态图，由 Agent 根据问题意图和复杂度动态判断是否需要 query 改写、混合检索和图谱推理，避免固定 RAG 流程在复杂业务问题上的局限。
7. 实现对话会话与记忆机制，使用 PostgreSQL 持久化 QA 消息和引用来源，Redis 维护短期滑动窗口和自动摘要，并预留 Mem0 长期记忆接入，用于多轮对话中的上下文补全和指代消解。
8. 实现企业级权限控制，支持私有、部门、公开三类文档可见范围，并将权限过滤下推到文档列表、BM25 检索、pgvector 召回和图谱召回链路，避免用户在问答中越权访问知识内容。
提供 SSE 流式问答和引用溯源能力，模型回答过程中按 token 流式返回，最终附带引用文档、chunk、片段摘要和相关性分数，提升问答过程的可用性和可信度。
